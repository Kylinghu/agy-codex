# AGY Codex v0.3.0 重构方案独立技术评审

- **评审对象**：[`docs/v0.3-adaptive-runtime-refactor.md`](./v0.3-adaptive-runtime-refactor.md)（基线提交 `66e1c43` / 文档提交 `841bcbd`）
- **评审依据**：当前仓库全量运行时源码、本机 `codex-cli 0.171.0` 与 Antigravity 宿主实测、提案引用的 7 个上游仓库元数据与核心源码
- **评审立场**：以工程实效与交互体验为核心，不默认认同提案；对不合理部分直接推翻并给出更简替代方案

## 1. 总体判断

**结论：问题诊断的大方向正确，但重构方案本身明显过度设计，且存在两处足以让实现走偏的核心架构失误。建议不要按当前 6 阶段 / 17 文件 / 13 命令的蓝图开工，应大幅瘦身后分 3 个短切片落地。**

### 认可的部分（保留方向）

1. **核心定位修正正确**：v0.2 把所有文件修改都绑死在“Git 仓库 + 全量快照 + 强制 `test_commands` + 固定 `WORKER_SCHEMA` + 强制 `research` 复审 + 每步新 Session”的单一重型状态机上，确实导致普通任务编排税远大于收益。将“执行能力”与“严格工程门禁”解耦是正确方向。
2. **依赖倒置正确**：当前 `backends/codex_app_server.py` 与 `inbox.py` 反向导入 `controller.py` 并直接读写 `Ticket` 状态，确实必须先切断这层耦合，避免在 `Controller` 上叠 `lightweight=True` 补丁。
3. **保留已验证的硬资产正确**：Windows 绕过 `.cmd`/`.ps1` shim（`resolve_codex`）、`WindowsJob(KILL_ON_JOB_CLOSE)` + `_child-gate`、Windows 共享冲突重试（`_metadata_io`）、按活跃 Turn 归属去重的 `RoundUsage`、不确定提交的只读对账（`reconcile`）都已付出真实调试成本，应当保留。

### 必须推翻或重写的 5 个核心问题

1. **最大架构失误：照搬 Claude Code 生态的 `--background` + `wait` + `events` 后台监督模型，无视 Antigravity 原生 `run_command` 异步任务与唤醒机制**，不仅多造了一套复杂子系统，还会在 Windows 上直接引发 `WindowsJob` 进程所有权悖论（要么随 CLI 退出被杀，要么逃逸成孤儿进程）。
2. **过度拆解与实体膨胀**：为了“轻量化”，提案反手设计了 **17 个 Python 模块、4 个领域实体（`Workspace`/`Session`/`Job`/`Ticket`）、13 个原子 CLI 命令**，比 v0.2（12 个脚本）更重，且与 Codex 原生 Thread 存储制造双份真相。
3. **事实错误与原生能力漏用**：提案阶段 01 要求实测对比 `codex mcp-server`，但本机实测 **`codex-cli 0.171.0` 已不存在 `codex mcp-server` 子命令**；同时忽略了本机 Codex 已原生支持的非 Git `thread/start`、`--skip-git-repo-check`、`thread/list`、`review/start`、`TurnStartParams.sandboxPolicy` 和 `windowsSandbox/readiness`。
4. **对“1 小时 / 8 轮”真实事故的归因偏差**：实测本机 Python 确实缺少 `python-docx`/`openpyxl`，且 Windows 沙盒下 COM `0x80080005` 源于硬编码 `sandbox="workspace-write"` + `WORKER_SCHEMA` 强制 `blocked` 拦截。提案把大量笔墨放在运行时分拆与通用作业模型上，却没有在运行时接口层给出沙盒策略可配置性和热路径开销消除方案。
5. **实施路径过长且顺序倒置**：先做不存在的 `mcp-server` 调研，再在长分支里大拆 17 个文件，拖到第 6 阶段才验证体验。实际上用 3 个小切片就能在第一周先解决 90% 的痛点。

## 2. 本机实测事实与提案偏差核对

本轮在当前目标机（Windows, Python 3.12.10, `codex-cli 0.171.0`）执行了只读探针（零模型推理调用），核实结果如下：

| 核查项 | 提案假设 | 本机实测结果 | 对设计的影响 |
|---|---|---|---|
| `codex mcp-server` | §2/§6/§11 阶段 01 要求对照测试 `codex` / `codex-reply` | **`codex help mcp-server` 报错 `unrecognized subcommand 'mcp-server'`（退出码 2）**；`codex mcp-server --help` 回退为顶层交互帮助 | **直接删除阶段 01 的 MCP 对照项**，不要浪费时间 |
| App Server 非 Git 启动 | 未实测 | 临时非 Git 目录执行 `initialize` 耗时 **360 ms**，`thread/start` 耗时 **719 ms**，返回 `ok=True` 与有效 `thread_id`，无需任何额外参数 | App Server 原生已支持非 Git 目录，冷启动总开销仅 ~1.1 s |
| `codex exec` 非 Git 支持 | 未明确参数 | `codex exec --help` 与 `codex exec resume --help` 均原生支持 `--skip-git-repo-check` | `backends/codex_exec.py` 只需补传该参数即可兼容非 Git |
| `codex app-server daemon` | 提案拒绝引入跨项目 Broker | CLI 存在 `codex app-server daemon`，但本机默认未启动（`daemon version` 报 `os error 10050` 连接 `.codex\app-server-control\app-server-control.sock` 失败） | **维持每轮独占 stdio `app-server` 是正确的**（仅 360 ms 启动成本，比依赖未启动 daemon 可靠得多） |
| `user_cli.py models` 耗时 | §9.3 提议缓存目录 | 单次执行耗时 **2,781 ms**（`config/read` + `modelProvider/list` + `model/list` + `account/rateLimits/read`） | 真正的问题不是 `models` 命令，而是 `codex_app_server.py:220-223` 在**每次 `run()` 热路径都重复调用 `discover()`** |
| `user_cli.py doctor` 耗时 | 未量化 | 单次执行耗时 **912 ms**（顺序拉起 4 个 `codex` 子进程 + Git 检查） | `agy_adapter.py:27` 每次进工作流都跑一遍静态 `doctor()`，属于可省的固定开销 |
| Windows 沙盒就绪检查 | 未提及 | App Server 原生提供 `windowsSandbox/readiness` RPC，本机返回 `{'status': 'ready'}`（耗时 **0 ms**） | 可直接接入 `doctor`，替代手工猜测沙盒状态 |
| 本机 Office Python 库 | §1 报告缺少库；§8.3 建议 Worker 选用 `python-docx`/`openpyxl` | 本机 `python-3.12.10` 实测：`docx=False, openpyxl=False, pptx=False, pypdf=False, fitz=True` | **仅在 Skill 里写“避免手搓 OOXML、优先用专业库”在当前环境不成立**——无库且沙盒禁网时 Worker 仍会碰壁 |
| Codex 原生协议能力 | §5/§6 计划自建 `sessions` 注册表与 `review` 封装 | `codex app-server generate-json-schema` 显示已原生具备：`thread/list`（支持 `cwd` 过滤）、`thread/fork`、`review/start`、`TurnStartParams.sandboxPolicy`（含 `writableRoots`/`networkAccess`）、`approvalsReviewer: "auto_review"` | 不必自建独立 Session 注册表；代码审查可直接复用原生 `review/start` 或 `codex exec review` |

## 3. 源码级问题与真实开销定位

对照仓库源码，当前 v0.2 的主要痛点与源码位置非常集中，远不需要推倒重写 17 个文件：

1. **硬编码 `research` 子代理导致普通与严格任务中断**
   - 位置：[`skills/agy-codex/scripts/agy_adapter.py#L58-L60`](../skills/agy-codex/scripts/agy_adapter.py#L58-L60)
   - 问题：`reviewer = agent_fn(role="AGY read-only reviewer", type_name="research", workspace="inherit")` 写死宿主私有的 `research` 名称；同时 [`agents/agy-codex.md#L10-L16`](../agents/agy-codex.md#L10-L16) 声明的工具集不含 `invoke_subagent`，主 Agent 无法按需委派轻量只读审查，也迫使所有执行都必须绕道 `/run-workflow`。
2. **每轮 9～11 次全仓库 SHA-256 扫描（文档/大仓库隐形杀手）**
   - 位置：[`skills/agy-codex/scripts/controller.py#L439-L472`](../skills/agy-codex/scripts/controller.py#L439-L472)（`snapshot()`）
   - 问题：单轮 Ticket 生命周期内 `snapshot()` 被重复调用近十次：`plans.py:160`（`start_plan`）→ `controller.py:500,501,513`（`create` 内连扫 3 次，外加 `_capture_files` 拷贝并再算一遍 SHA-256）→ `controller.py:641`（`run`）→ `controller.py:838,878,882`（`_prepare_review` 连扫 3 次，外加 `_task_diff` 复制并再校验 `baseline-files`）→ `controller.py:907`（`packet`）→ `controller.py:923`（`verdict`）→ `product.py:121`（连只读 `status` 都全仓算 SHA-256！）。面对 25 MB+ 的 Office 二进制资料，这会触发数百 MB 级重复磁盘读写，且 `_task_diff` 用 `git diff --binary` 对 `.xlsx`/`.docx` 生成无意义的大体积二进制补丁。
3. **热路径每次 `run()` 重复做 `discover()` 模型目录发现**
   - 位置：[`skills/agy-codex/scripts/backends/codex_app_server.py#L220-L223`](../skills/agy-codex/scripts/backends/codex_app_server.py#L220-L223)
   - 问题：只要指定了 `model` 或 `model_provider`，每次执行都先跑 `config/read` + `modelProvider/list` + `model/list`，额外浪费 1～2 秒。模型有效性校验完全可以交给 `thread/start` / `turn/start` 自身报错，或复用轻量缓存。
4. **强耦合 Git、强制 `WORKER_SCHEMA`、强制 `test_commands`、强制每 Ticket 新 Session**
   - 位置：
     - `controller.py:380-382`：`Controller.__init__` 强依赖 `git rev-parse`，非 Git 目录直接报错。
     - `controller.py:360-362`：`validate_spec` 强制非空 `test_commands`。
     - `controller.py:505` / `plans.py:179`：每个 Ticket 固定 `session_id=None`，无法跨相关步骤复用上下文。
     - `codex_app_server.py:224,301` 与 `codex_exec.py:6,11`：硬编码 `sandbox="workspace-write"`、`approvalPolicy="never"` 和 `outputSchema=WORKER_SCHEMA`。
     - `controller.py:948-952`：只要 Worker 报告了 `blocked`/`permission`（例如 Office COM `0x80080005` 渲染验证失败），即使交付文件本身完好，也强制跳过所有验收并禁止 `PASS`，触发反复返工。
5. **后端反向依赖 `controller.py`**
   - 位置：`backends/codex_app_server.py:16`、`backends/codex_exec.py:2`、`backends/usage.py:7`、`inbox.py:16`、`progress.py:9`、`routing.py:6`、`config.py:7`。
   - 问题：`controller.py` 既充当底层工具库（`WorkflowError`、`atomic_json`、`WindowsJob`、`stop_process`、`resolve_codex`），又是 Strict 状态机本体，导致任何调用后端的代码都必须加载整个 `Controller`。

## 4. 关键架构评议与替代设计

### 4.1 推翻“自建 `--background` 监督器 + `wait` + `events` 游标”，直接复用 Antigravity 原生 `run_command` 异步生命周期

这是本评审最核心的架构修正意见。

**提案的做法（§6、§9.1、§9.2）**：借鉴 `openai/codex-plugin-cc` 与 `porch`，设计 `delegate --background` 启动独立持有 `WindowsJob` 的后台进程，再由 Gemini 调用 `wait --job JOB-001 --timeout 60`、`events`、`result`、`cancel`。

**为什么这套设计在 Antigravity + Windows 上是错的**：

1. **它解决的是 Claude Code 的限制，不是 Antigravity 的问题**。Claude Code 的 `Bash` 工具缺乏原生的长任务托管与完成唤醒，所以 `codex-plugin-cc` 才被迫造出 `app-server-broker.mjs` + `tracked-jobs.mjs`，`porch` 才被迫造出 POSIX `--detach` supervisor + `wait` 轮询循环。
2. **Antigravity 的 `run_command` 本身就是宿主级异步任务管理器**：
   - 支持 `WaitMsBeforeAsync`（短任务 10 秒内同步返回，零额外轮次）；
   - 超时自动转入宿主后台任务，主对话立即保持可交互；
   - 支持 `NotificationTimeoutSeconds`（**天然实现“观察超时不杀 Worker”**，无需自建 `wait --timeout`）；
   - 任务结束时**宿主被动唤醒 Gemini**（零轮询、零 `wait` 循环消耗模型轮次）；
   - 原生提供 `manage_task`（`list` / `status` / `send_input` / `kill`）与侧边栏 Background Tasks 视图。
3. **Windows `WindowsJob` 所有权悖论（致命缺陷）**：
   - 若 `delegate --background` 退出后，后台监督进程仍在 AGY 的作业对象树内，AGY 清理命令子进程时可能一并杀掉后台监督器；
   - 若后台监督进程使用 `CREATE_BREAKAWAY_FROM_JOB` 脱离 AGY 作业对象以求存活，那么当用户取消对话、点击停止或关闭 Antigravity 时，**没有任何进程持有它的生命周期句柄**，Codex 会变成孤儿进程继续在后台改写用户文件，直接违背 AGY Codex 最核心的安全资产。

**替代架构（推荐）**：

- `user_cli.py run` **永远是单一前台进程**，直接持有 `WindowsJob(KILL_ON_JOB_CLOSE)`（POSIX 上持有 `start_new_session` 进程组）。
- Gemini 通过 `run_command(CommandLine="... user_cli.py run ...", WaitMsBeforeAsync=10000, NotificationTimeoutSeconds=120)` 调用：
  - **快任务（≤10s）**：同轮直接拿到结果，0 次额外工具调用、0 次 `wait`；
  - **长任务（>10s）**：宿主自动切后台；运行期间 `user_cli.py run` 将去重节流后的关键进度行实时打印到 stdout/stderr（同时写 `progress.json`），用户在对话里问进度时 `manage_task(status)` 或 `user_cli.py status` 即可看到最新进展；
  - **中途纠偏 / 软中断**：主对话用另一条独立 `run_command` 调用 `user_cli.py inbox steer|queue|interrupt`（不拿锁，保留现有 Maildir 原子投递机制）；
  - **强制取消 / 宿主退出**：`manage_task(kill)` 或关闭宿主 → 杀掉 `user_cli.py run` → `WindowsJob(KILL_ON_JOB_CLOSE)` 确定性清理整个 Codex 进程树，无任何孤儿进程风险！
- **收益**：直接砍掉 `--background` 脱离监督器、`wait` 命令、`events --cursor` 游标接口，以及一整套跨进程生命周期状态机。

> **需要本机实测确认的一点**：在 Antigravity 2.0 桌面版中，验证“主对话发起 `run_command` 进入后台后，用户继续发消息时 Gemini 能否并发执行第二条 `run_command`（`inbox steer`）”，以及 `manage_task(kill)` 触发时 `WindowsJob(KILL_ON_JOB_CLOSE)` 是否完整清理 Codex 孙进程。这只需 10 分钟实机验证，且应在写代码前完成。

### 4.2 精简领域模型与 CLI：去掉独立 `Session` 注册表，13 命令收口为 5～6 个

**提案问题（§5、§6）**：同时维护 `Workspace`、`Session`、`Job`、`Ticket` 四类持久化对象与 13 个命令。

**评议**：

1. **不要自建 `Session` 注册表**：Codex CLI 自身在 `$CODEX_HOME` 中维护 Thread 存储，且 App Server 已提供 `thread/list(cwd=...)`、`thread/read`、`thread/turns/list`。在插件侧再建一套 `sessions.py` 状态库，必然与用户直接在 Codex CLI/Desktop 归档、删除或续跑的会话产生双份真相漂移。
2. **用单一 `Run` 对象统一普通执行与 Strict 回合**：
   - `Run` 对应一次 Codex 调用（等同提案的 `Job`），字段极简：`run_id`, `workspace_key`, `cwd`, `thread_id`, `continued_from`, `model_provider`, `backend`, `codex_requested`, `sandbox`, `status`（`running/completed/failed/interrupted/unknown`）, `turn_pending`, `active_turn_id`, `inbox_window`, `pid`, `usage`, `result_path`, `started_at`, `ended_at`。
   - **如何避免 `Run` 与 `Ticket` 两套状态**：`Ticket` 不再直接保存 `app_server_pending`、`active_turn_id`、`inbox_window`；每个 Ticket 回合仅保存 `run_id`（并在首轮绑定 `session_id`）。恢复对账（`reconcile(run_id)`）和实时消息（`inbox`）全局只有一套实现，全部绑定到 `run_id`。
   - “查询可恢复会话”只需读该工作区最近 `Run` 索引（或按需调 `thread/list`），无需独立实体层。
3. **CLI 从 13 个命令收口为 5 个核心命令**（保留现有 Strict `/run-workflow` 入口兼容）：

| 建议命令 | 替代提案中的哪些命令 | 说明 |
|---|---|---|
| `run` | `delegate` + `resume` + `review` + `result` | 前台执行；`--resume <run_id\|thread_id\|last>` 续跑（`last` 仅限本插件在该工作区记录的最近 `Run`，不盲猜全局 `--last`）；`--review` 可触发原生 `review/start` 或 `codex exec review`；`--sandbox` 支持 `read-only`/`workspace-write`（显式配置才允许更宽）；`--schema` 默认为空，Strict 模式显式传入；退出时输出紧凑 JSON/文本摘要含 `result_path` |
| `status` | `status` + `sessions` + `events`（只读） | 读取当前工作区活跃/近期 `Run`、最新 `progress.json`、以及（若存在）活跃 Strict Ticket/Plan 摘要；**绝不触发全仓 SHA-256**，零模型调用 |
| `inbox` | `steer` + `queue` + `interrupt` + `cancel` | 沿用现有无锁 Maildir 语义（`steer` / `queue` / `interrupt` / `status`），改以 `run_id`（默认当前活跃 Run）为锚点；硬取消走宿主 `manage_task(kill)` |
| `models` | `models` | 只读能力目录 + 额度查询；支持轻量本地缓存（如 15 分钟 TTL，配置/Provider 变更失效，额度支持 `--refresh`） |
| `doctor` | `doctor` | 兼容非 Git 目录（非 Git 时标 `git_repository: false` 作为信息而非阻塞失败）；增加 `windowsSandbox/readiness` 检查与当前 Python 常见环境诊断 |

> 删去的命令：`wait`（由 AGY `run_command` 异步唤醒替代）、`events`（由前台流式节流 stdout + `progress.json` 替代）、`result`（`run` 返回即含 `result_path`，`status --json` 也可取回）、独立的 `delegate`/`resume`/`review`/`cancel`/`sessions`（合并减少心智与维护面）。

### 4.3 精简模块划分：从 17 个文件压回 6～7 个高内聚模块

提案 §10 建议拆出 `runtime/{workspace,jobs,sessions,process,storage,events,inbox}.py` + `strict/{controller,plans,validation,review}.py` 共 17 个脚本。对于当前仅 ~2,600 行 Python 的标准库插件来说，这是典型的“为目录美观而过度切碎”，会带来大量跨文件导入胶水与测试迁移成本。

**更务实的模块结构**：

```text
skills/agy-codex/scripts/
├── runtime.py                 # 底层公共内核：Workspace 身份与锁、WindowsJob/_child-gate、atomic_json/_metadata_io、Run 记录与对账
├── inbox.py                   # 绑定 run_id 的无锁 Maildir（解除对 controller.py 的导入）
├── progress.py                # 通用事件投影 + 节流 stdout/progress.json（移除写死的 12 条上限，改为去重+最小间隔）
├── config.py                  # 配置读取（兼容 v0.2）
├── routing.py                 # 档位策略、Provider 校验、轻量目录缓存
├── user_cli.py                # 统一轻量入口：run / status / inbox / models / doctor
├── backends/
│   ├── codex_app_server.py    # 仅依赖 runtime/inbox/usage；outputSchema 可选；支持非 Git 与可配 sandboxPolicy
│   ├── codex_exec.py          # 仅依赖 runtime；补 --skip-git-repo-check；outputSchema 可选
│   └── usage.py               # 仅依赖 runtime.atomic_json/read_json
├── controller.py              # Strict Workflow（Ticket/基线/Diff/验收/裁决），改为消费 runtime + backends
```

- 依赖方向同样严格单向：`strict(controller/plans/product/agy_adapter)` → `runtime` → `backends`，彻底消除反向依赖；
- `user_cli.py`、现有 10 个测试文件、安装脚本的路径冲击降到最低；

### 4.4 非 Git 工作区身份、存储路径与单写入锁兼容方案（补齐提案空白）

提案 §8.2 要求支持非 Git 工作区，§14.4 追问非 Git 锁如何兼容 Strict，但提案正文未给出具体落盘设计。明确建议如下：

1. **存储与锁路径规则（统一由 `runtime.resolve_workspace(cwd)` 决定）**：
   - **Git 仓库内**：沿用 `<gitdir>/superagent/`，锁路径仍为 `<gitdir>/superagent/worktree.lock`。100% 兼容旧 Ticket/Plan，且天然隔离不同 Git worktree。
   - **非 Git 目录**：按规范化路径（Windows 下 `os.path.normcase(str(Path(cwd).resolve()))`）计算 SHA-256 前 16 位，存储于 `~/.gemini/config/agy-codex/workspaces/<hash16>/`（支持 `AGY_CODEX_STATE_DIR` 覆盖），锁文件为该目录下的 `workspace.lock`，同时写 `workspace.json` 记录原始规范路径。
   - **绝对不要**在用户的非 Git 文档目录中创建 `.agy-codex/`，避免污染待交付的文档文件夹。
2. **与 Strict 模式共存的防冲突边界**：
   - 在 Git 仓库中，轻量 `run` 和 Strict `Controller` **共用同一把 `worktree.lock`**，保证任何时候同一工作树最多只有一个写入者。
   - 如果该 Git 仓库存在未结束的 Strict Ticket（`active.json` 指向非终态或待复审任务），轻量 `run` 默认拒绝静默写入并提示用户（除非显式 `--ignore-strict` 或先结束/继续该 Ticket），彻底避免轻量调用破坏 Strict 的 `expected_sha256` 快照。

### 4.5 彻底解决 `research` 缺失与主 Gemini 复核路径

1. **普通任务不再经过 `/run-workflow`**：
   - 普通委派、续跑、轻量文档或代码修改直接由主 Gemini 调 `run_command` 运行 `user_cli.py run`。
   - 完成后，主 Gemini 直接拿到 `result.md`、变更文件列表、命令记录与用量，自行用 `read_file` 抽检关键改动并向用户汇报——**彻底绕开 `research` 子代理依赖，也省去 `/run-workflow` 启动开销**。
2. **Strict 模式或显式要求独立复审时**：
   - 立即移除 `agy_adapter.py:60` 对 `type_name="research"` 的硬编码。
   - **首选方案**：在插件内自带一个极简只读子代理定义 `agents/agy-codex-reviewer.md`（`mainAgent: false`, `subagent: true`, `model: inherit`, `tools: [read_file]`），并允许 workflow 参数 `reviewer_type` 覆盖；若宿主环境不支持自定义子代理名，在显式降级或配置下使用 `type_name="self"`（`run-workflow` 文档明确保证 `"self"` 总是存在，配合 `controller.py` 既有的快照防篡改校验即可兜底只读性）。
   - **替代独立复审**：如果用户需要独立第二视角审查代码改动，Codex 自身已原生支持 `review/start` / `codex exec review --uncommitted`，可直接作为零额外编排的独立代码审查选项。
   - 保持提案 §7 的底线：明确要求独立复审的 Strict 任务，在无法启动独立审查者时如实保留 `REVIEW` 状态与证据，不拿主对话草率冒充。

## 8. 性能与体验验收修正建议

提案 §12 的整体对照思路是对的，但存在**变量混杂**和**Windows 关键边界漏测**两个问题，建议修正为两组独立测试：

### A 组：严格受控编排税测试（同模型、同推理深度、同环境库、同输入）
- 对比对象：原生 `codex exec` / `app-server` vs v0.2 AGY Codex vs v0.3 AGY Codex（轻量 `run`）。
- 场景：
  1. **单文件小修改**（Git 仓库）
  2. **非 Git 目录两步关联任务**（复用 Session）
- 验收标尺：
  - v0.3 轻量 `run` 相比原生 Codex，额外编排耗时 **< 3～5 秒**（剔除模型本身耗时），额外模型调用 **= 0**，观察与状态查询模型调用 **= 0**；
  - 关联任务第二步成功复用同一 `thread_id`，无需重新注入全量上下文。

### B 组：真实端到端效能与交互回归（允许 v0.3 使用自适应档位与不强制复审）
- 场景：
  1. **非 Git 三份关联文档生成**（含大体积源资料，统一预先确认所需 Python 库或 HWB 工具状态，不把“缺库环境故障”混进运行时耗时）：记录总 wall time、总模型调用次数、已观测 Token、资料解析次数、用户干预次数与交付质量。
  2. **长任务交互测试**：运行 >60s 任务，验证 `NotificationTimeoutSeconds` 观察超时不中断、主对话并发 `inbox steer` 生效、`inbox interrupt` 保留进度与 Session。
  3. **Windows 强杀无残留测试**：运行会派生子进程的任务，用 `manage_task(kill)` 终止，核实 `node.exe` / `codex` / 孙进程数为 0，锁已释放。
  4. **非 Git 中文/空格路径与零污染测试**：在类似 `D:\测试文档\项目 A` 路径执行，确认工作目录内未生成任何隐藏元数据文件。
  5. **Strict 共存与旧记录兼容测试**：在已有未完成 v0.2 Ticket 的 Git 仓库中验证旧任务可恢复，且轻量 `run` 不会静默破坏其基线快照；复杂代码改造走 Strict 模式时独立验收与双轴复审不降级。
